# 분석 파이프라인 비동기화 — 갭 분석 & 단계별 계획

작성일: 2026-07-08
대상: `backend`의 영상 분석 실행 경로 (`AnalysisCommandService`, `AsyncConfig`, watchdog 등)

---

## 1. 확인한 현재 상태 (이미 잘 되어 있는 것)

비동기 구조는 이미 대부분 구현되어 있습니다. 코드 기준으로 확인한 사실입니다.

- **업로드와 실행이 분리됨.** `POST /api/analysis/upload`로 파일만 저장하고 job은 `UPLOADED` 상태로 만든 뒤, `POST /api/analysis/{jobId}/run`으로 분석을 시작합니다.
- **`/run`은 즉시 응답함.** 상태를 "시작됨"으로 바꿔 DB에 커밋하고, 트랜잭션 커밋 직후(`afterCommit`) 백그라운드 스레드 풀(`analysisTaskExecutor`)에 실제 작업을 넘깁니다. HTTP 요청 안에서 분석을 끝까지 기다리지 않습니다.
- **상태·진행률 조회 구조가 있음.** 최종 상태는 MySQL(`AnalysisJob`)에, 진행 중 퍼센트는 Redis에 잠깐 저장(TTL 2시간)합니다. Redis가 죽어도 DB 상태로 대략적인 진행률을 대체 표시합니다. (`/status`, `/progress`)
- **취소·재시도·재시도 상한이 있음.** 취소는 `cancel_requested` 플래그로 단계마다 확인하는 협조적(cooperative) 방식이고, 재시도는 `retry_count`와 최대 횟수 제한이 있습니다.
- **멈춘 작업 복구가 있음.** `StuckAnalysisJobWatchdogService`가 스케줄(기본 10분마다, 분산 락 사용)로 30분 넘게 "실행 중"인 job을 찾아 자동 실패 처리합니다.
- **소유권 검증·경로 검증이 있음.** jobId 형식 검사(경로 조작 방지), 요청자와 job 소유자 일치 검사가 이미 들어가 있습니다.
- **운영 편의 요소.** 메트릭(Micrometer), 로그에 jobId 심는 MDC 전파, 종료 시 진행 작업 대기(graceful shutdown)까지 있습니다.

**결론: "동기 요청 기반 → 비동기 job 기반" 전환은 사실상 완료 상태입니다.**

## 2. 발견한 문제 (진짜 남은 갭)

핵심은 하나입니다. **큐와 워커가 백엔드(backend) 프로세스 안에 그냥 스레드 풀로 들어가 있다**는 점. 여기서 파생되는 위험을 순서대로 정리합니다.

### G1. CallerRunsPolicy 모순 (가장 시급)
스레드 풀과 대기열(큐 용량 20)이 **둘 다 꽉 차면**, 설정상 `CallerRunsPolicy`라서 **요청을 보낸 HTTP 스레드가 직접 분석 파이프라인을 실행**합니다. 즉, 사람이 몰리는 바로 그 순간에 우리가 그렇게 피하려던 "HTTP 요청 안에서 무거운 영상 분석을 끝까지 처리" 상황이 되살아납니다. 요청은 수 분간 응답하지 않고, 그 요청 스레드가 묶여 다른 API 응답까지 느려집니다.

### G2. 워커가 독립 배포 단위가 아님 (CLAUDE.md 2번 항목)
분석 실행과 API 서버가 같은 JVM입니다. 분석 부하가 커지면 로그인·조회 같은 일반 API 응답까지 같이 느려지고, "분석 워커만 늘려서 확장"하는 게 불가능합니다.

### G3. 큐가 프로세스 메모리에 있어 재시작에 약함
대기열(큐)은 JVM 메모리 안에 있습니다. 배포·재시작·크래시가 나면 **아직 시작 안 한 대기 작업은 흔적 없이 사라지고**, 실행 중이던 작업은 30분 뒤 워치도그가 "실패"로 처리할 때까지 사용자 화면에서 계속 "분석 중"으로 멈춰 보입니다.

### G4. 워치도그는 "실패"만 하고 "재개"는 안 함
서버 재시작으로 끊긴 작업을 워치도그가 실패 처리는 하지만, 자동으로 다시 실행(resume/re-queue)하지는 않습니다. 사용자가 직접 재시도를 눌러야 합니다.

### G5. 타임아웃이 워치도그(30분)에 의존
개별 작업 단위의 강제 타임아웃이 없습니다. 외부 호출(analysis-engine 등) 하나가 오래 매달리면 그 워커 스레드는 최대 30분까지 붙잡힙니다.

### G6. 취소가 외부 호출 도중에는 안 먹힘
취소 플래그는 단계와 단계 "사이"에서만 확인합니다. 긴 analysis-engine 호출이 진행 중이면 그 호출이 끝날 때까지 취소가 반영되지 않습니다.

## 3. 단계별 실행 계획 (작게 나눠서)

기존 인프라(MySQL, Redis)를 그대로 쓰고 새 브로커 도입은 최소화하는 방향입니다. 각 단계는 독립적으로 배포·검증 가능하도록 나눴습니다.

### 1단계 — 가장 위험한 모순부터 제거 (작음, 코드 변경 적음)
- `CallerRunsPolicy`를 제거하고, 풀·대기열이 꽉 차면 **HTTP 스레드가 대신 실행하지 않고** 사용자에게 "지금 분석 요청이 많습니다. 잠시 후 다시 시도해 주세요"를 명확한 상태 코드(예: 429)로 돌려줍니다.
- 이때 job은 "시작됨"으로 잘못 바뀌지 않도록, 큐에 넣는 데 성공한 뒤에만 상태를 전이하도록 순서를 점검합니다.
- 검증: 동시 요청 부하 테스트로 큐가 찰 때 API 응답이 계속 빠른지 확인.

### 2단계 — 큐를 지속성 있게 만들기 (중간)
- 작업을 메모리 큐가 아니라 **DB(또는 Redis)에 `PENDING`으로 적재(enqueue)**하고, 워커가 그걸 집어(polling 또는 Redis `BRPOP`/Streams) 실행하도록 바꿉니다.
- 재시작해도 대기 작업이 보존되고, 워치도그를 "실패"에서 "**다시 큐에 넣기(re-queue)**"로 확장할 수 있게 됩니다(G3, G4 해결).
- 정량 분석 결과는 손대지 않고, "언제 누가 실행하느냐"만 바꿉니다.
- 검증: 대기 중/실행 중 상태에서 백엔드를 강제 재시작한 뒤 작업이 유실 없이 이어지는지 확인.

### 3단계 — 워커를 별도 실행 단위로 분리 (중간, CLAUDE.md 2번 충족)
- 같은 코드베이스를 `--worker` 프로파일로 띄우면 **API는 처리하지 않고 큐만 소비**하도록 분리합니다.
- `docker-compose.yml`에 `analysis-worker` 서비스를 추가하고, 백엔드는 enqueue만, 워커는 consume만 하도록 역할을 나눕니다. 워커만 여러 개로 늘려 수평 확장이 가능해집니다(G2 해결).
- 검증: 워커 컨테이너를 껐다 켜도 백엔드 API 응답이 영향받지 않는지, 워커 2개일 때 병렬 처리가 되는지 확인.

### 4단계 — 타임아웃·취소 정교화 (작음~중간)
- 작업 단위 강제 타임아웃을 두고, 초과 시 자동 실패+재큐 정책을 적용합니다(G5).
- 외부 호출 클라이언트 타임아웃과 취소 신호를 연동해, 긴 호출 도중에도 취소가 비교적 빠르게 반영되도록 개선합니다(G6).
- 검증: 인위적으로 느린 응답을 만들어 타임아웃·취소가 제시간에 동작하는지 확인.

---

## 4. 남은 위험 / 주의
- 2단계에서 큐 저장소로 Redis를 쓰면 "정확히 한 번" 보장이 아니라 "적어도 한 번" 실행이 되므로, 같은 작업이 두 번 실행돼도 결과가 꼬이지 않도록 멱등(idempotent) 처리를 함께 설계해야 합니다.
- 3단계에서 워커 분리 시, 파일 저장 경로(storage)와 DB·Redis 접근을 워커도 동일하게 갖도록 배포 설정을 맞춰야 합니다.
- 모든 단계에서 정량 분석 수치는 변경하지 않습니다. LLM은 점수 산출자가 아니라 해석·피드백 생성자로만 유지합니다.

## 5. 실행한 검증 (이번 계획 단계)
- 코드 파일 직접 확인만 했고, 아직 어떤 코드도 수정하거나 테스트를 돌리지 않았습니다. 이건 갭 분석 + 계획 문서입니다.

## 6. 다음 우선순위 (승인 요청)
1단계(CallerRunsPolicy 모순 제거 + 큐 가득참 시 명확한 429 응답)부터 착수할 것을 제안합니다. 변경 범위가 가장 작고, 가장 위험한 문제를 먼저 없앱니다. 승인해 주시면 1단계 구현에 들어가겠습니다.
