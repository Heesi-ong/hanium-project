# 비동기 분석 큐: 메시지 브로커 전환 평가 및 단계적 계획

작성일: 2026-07-17
상태: **설계/평가 문서(승인 전).** 코드는 아직 바꾸지 않았습니다. 이 문서는 L5("DB 폴링 claim 큐 → 진짜 메시지 브로커") 갭에 대해 현재 구조를 정확히 분석하고, 브로커 도입이 실제로 언제·왜 필요한지와, 도입한다면 어떻게 **작게·되돌릴 수 있게** 진행할지 정리합니다.
용어는 처음 나올 때 괄호로 풀어서 적었습니다.

## 0. 요약 (결론 먼저)

현재의 "DB 폴링 claim 큐"는 흔히 생각하는 단순 폴링이 아니라, **행 잠금 기반 원자적 선점(claim) + 워커 수평 확장 + 재시작 복구 + 워치독 + 재시도 + 백프레셔**까지 갖춘 성숙한 구조입니다. 진짜 브로커(RabbitMQ/Redis Streams/SQS)가 이 위에 더해주는 것은 사실상 네 가지뿐입니다: **(1) 데드레터 큐(DLQ), (2) 우선순위 큐, (3) 지수 백오프 재시도, (4) push 방식(폴링 지연 제거)**.

이 네 가지 중 (1)~(3)은 **브로커 없이 지금 DB 모델 위에서 값싸게 채울 수 있습니다.** 새 인프라(브로커 컨테이너, 그 자체의 장애 모드/운영 부담)를 들이는 것은 **명확한 트리거**(아래 5장)가 생기기 전에는 비용 대비 이득이 낮습니다.

**권장 경로: 브로커를 지금 도입하지 않습니다.** 대신 (A) DB 큐 위에서 DLQ·백오프·우선순위 갭을 단계적으로 메우고, (B) 브로커 도입 트리거를 명시적으로 정의해 두었다가 트리거가 실제로 발생하면 그때 **이미 Redis에 의존하고 있으므로 Redis Streams**로 전환합니다. 각 단계는 기존 동작을 유지한 채 되돌릴 수 있게 설계합니다.

## 1. 현재 구조 (코드 근거)

- **상태 모델**: `AnalysisJob`(엔티티)이 `UPLOADED → QUEUED → BASIC_ANALYZING → VIDEO_LLM_ANALYZING → COMPACTING → OPENAI_GENERATING → MERGING_RESULT → COMPLETED`, 실패 시 `FAILED`, 취소 시 `CANCELLED`. `@Version` 낙관적 락(동시 저장 시 한쪽만 성공).
- **접수**: `/run`은 job을 `QUEUED`로 저장만 하고(worker 분리 배포 시) 즉시 실행하지 않습니다. 단일 프로세스(monolith) 모드에서는 커밋 직후 로컬 executor로 바로 투입.
- **선점(claim)**: `QueuedAnalysisJobPoller`(`analysis.worker.poller.enabled=true`)가 1초 주기로 executor 여유 슬롯을 계산하고, 그만큼만 `claimNextQueuedJobs(limit)`로 가져옵니다. 이 쿼리는 `SELECT ... WHERE status=QUEUED ORDER BY createdAt ASC`에 **행 잠금 + 잠금 타임아웃 10초**(`jakarta.persistence.lock.timeout`)를 걸어 **조회와 동시에 원자적으로 QUEUED→BASIC_ANALYZING 선점**합니다. 여러 워커가 동시에 폴링해도 같은 후보를 중복 실행하지 않습니다(FIFO 보장).
- **실행**: 선점된 job만 `ThreadPoolTaskExecutor`(core/max/queue 환경변수)로 in-process 실행.
- **재시작 복구**: `QueuedAnalysisJobResumeService`(@Scheduled + Redis 분산 락)가 "접수된 지 오래됐는데 아직 QUEUED"인 유실 작업을 다시 투입. 선점은 QUEUED일 때만 성공하므로 중복 실행 없음.
- **멈춘 작업 처리**: `StuckAnalysisJobWatchdogService`가 실행 상태로 너무 오래 남은 job을 FAILED로 전이.
- **재시도**: `retryCount++` 후 `UPLOADED`로 되돌림, 최대 재시도 횟수(`ANALYSIS_RETRY_MAX_COUNT`) 제한.
- **백프레셔**: 전역 QUEUED 상한(기본 100)과 사용자별 QUEUED 상한(기본 3). 초과 시 429.
- **취소**: QUEUED면 즉시 CANCELLED, 실행 중이면 협조적 취소 플래그.

즉 "워커를 여러 개로 늘려도 안전하게 나눠 처리"하는 목표(L2/L5의 핵심)는 **이미 충족**되어 있습니다.

## 2. 진짜 브로커가 더해주는 것 vs 현재 갭

| 브로커 기능 | 현재 상태 | 실제 갭인가? |
|---|---|---|
| 워커 수평 확장·중복 실행 방지 | 행 잠금 claim으로 이미 보장 | 갭 아님 |
| 재시작 후 유실 작업 복구 | Resume 스케줄러로 보장 | 갭 아님 |
| 처리량 제한/백프레셔 | 전역·사용자별 QUEUED 상한 | 갭 아님 |
| **데드레터 큐(DLQ)**: 반복 실패 작업 격리·수동 재처리 | 재시도 소진 시 그냥 FAILED. "왜/몇 번 실패했는지 모아 보고 재처리"하는 격리 개념 없음 | **갭** |
| **지수 백오프 재시도**: 실패 후 점점 긴 간격으로 재시도 | 재시도는 **사용자 수동**(`retryAnalysis`/`/retry`, FAILED·CANCELLED일 때만). **자동 재시도 루프 없음** | **갭 아님**(아래 2.1 참고 — 백오프는 자동 재시도 폭주 방지용이라 수동 재시도 모델에선 오히려 UX만 악화) |
| **우선순위 큐**: 특정 작업 먼저 | 순수 FIFO(createdAt) | **갭**(현재는 필요성 낮음) |
| **push 방식**: 폴링 지연 제거 | 1초 폴링 지연 | 갭이지만 영향 미미(분석 자체가 수십 초~분 단위) |
| 브로커 자체 내구성/재전송 | DB가 사실상 내구성 저장소 역할 | 갭 아님(DB가 이미 durable) |

### 2.1 재시도 모델 재확인 (2026-07-17 코드 재검토)

당초 이 문서는 "실패 시 즉시 재실행 → 지수 백오프 필요"로 보았으나, `AnalysisCommandService.retryAnalysis`(200~214행)와 `validateRetryable`(770~792행)을 다시 읽어 확인한 결과 **재시도는 전적으로 사용자 수동**입니다. `/retry` 엔드포인트가 FAILED·CANCELLED 상태에서만, 소유권·재시도 한도(`ANALYSIS_RETRY_MAX_COUNT`) 검사 뒤 `resetForRetry()`→재큐합니다. 실패한 job을 **자동으로 다시 큐에 넣는 루프는 없습니다**(실패하면 `FAILED`로 남음).

따라서 **지수 백오프(1a)는 갭이 아닙니다.** 백오프는 "자동 재시도가 실패 중인 외부 의존성을 반복해서 두들기는 것"을 막는 장치인데, 재시도가 수동이면 두들김 자체가 없습니다. 오히려 백오프를 넣으면 사용자가 "다시 시도"를 눌러도 job이 대기 상태로 지연돼 **UX가 나빠집니다.** → **구현하지 않기로 결정.**

(만약 향후 "실패 시 자동 N회 재시도"를 도입한다면 그때 이 자동 재시도에 한해 백오프를 함께 넣는 것이 맞습니다. 현재 수동 모델에서는 불필요.)

**수정된 결론: 브로커가 더해줄 실질 갭은 사실상 (1b) DLQ 격리·가시성 정도로 축소됩니다. 백오프는 재시도 모델이 자동으로 바뀔 때까지 불필요하고, 우선순위는 요구가 없습니다.**

|---|---|---|---|---|

## 4. 권장 단계적 계획 (각 단계 가역적)

### 1단계 — DB 큐 보강 (브로커 없이 실질 갭 해소)

작게 나눠 순서대로. 각 단계는 Flyway 마이그레이션 1개 + 코드 소폭 + 테스트.

1a. ~~지수 백오프 재시도~~ — **철회(2026-07-17).** 2.1에서 확인했듯 재시도가 수동이라 백오프는 불필요하고 UX만 악화. "실패 시 자동 재시도"를 도입하는 시점에만 재검토.

1b. **데드레터 상태(DLQ)**: `AnalysisStatus`에 `DEAD_LETTER` 추가. 재시도 소진 시 `FAILED` 대신(또는 함께) `DEAD_LETTER`로 전이하고 `lastFailureReason`을 저장. 관리자 대시보드에 DLQ 목록·수동 재처리(“다시 큐에 넣기”) 액션 추가. → 반복 실패를 한곳에서 보고 재처리 가능. **되돌리기**: 상태를 안 쓰면 됨(기존 FAILED 경로 유지).

1c. **(선택) 우선순위**: `priority` 컬럼 추가, claim 쿼리 `ORDER BY priority DESC, createdAt ASC`. 실제 우선순위 요구가 생길 때만. 지금은 보류 권장.

**검증**: 각 단계 backend 단위/통합 테스트(claim 동시성, 백오프 조건, DLQ 전이, 재처리) + `./gradlew test`. 기존 claim 동시성 테스트(`AnalysisJobStatusServiceConcurrentClaimTest` 등)와 정합.

### 2단계 — Redis Streams 전환 (트리거 발생 시에만)

1단계로 대부분의 실익을 얻은 뒤, 5장 트리거가 실제로 관측되면 진행. DB는 job의 **진실 원천(source of truth)**으로 유지하고, Redis Stream은 "실행하라"는 **신호 전달 채널**로만 사용(상태·결과는 계속 DB). consumer group으로 워커 분배, `XPENDING`/`XCLAIM`으로 죽은 워커의 미완료 메시지 회수. **되돌리기**: `analysis.worker.poller.enabled`처럼 플래그로 폴러 방식과 Streams 방식을 토글 가능하게 설계.

### 3단계 — 전용 브로커 (원거리 미래)

다서비스 이벤트 기반 아키텍처나 초대규모가 될 때만 RabbitMQ/SQS 검토. 현재 로드맵에선 불필요.

## 5. 브로커(2단계 이상) 도입 트리거 — 이 중 하나가 관측되면 재검토

- 지속적으로 **분당 큐 유입이 폴링/claim 처리량을 초과**해 QUEUED 적체가 계속 쌓임(부하 테스트/`analysis_job_*` 메트릭으로 판단).
- **폴링 1초 지연이 제품 요구를 위반**(예: 준실시간 처리 요구).
- claim 쿼리의 **행 잠금 경합이 DB에 유의미한 부하**(잠금 타임아웃 빈발, DB CPU 상승).
- 분석 완료를 **다른 서비스들이 이벤트로 구독**해야 하는 요구 발생(이벤트 기반 확장).

트리거가 없으면 1단계 보강만으로 충분하며, 그것이 현재 권장입니다.

## 6. 남은 위험 / 주의

- 2단계(Redis Streams)는 DB와 Redis 두 곳에 상태가 생겨 **정합성**(job은 DB, 신호는 Redis)을 신중히 설계해야 합니다. "신호 유실 시 Resume 스케줄러가 DB 기준으로 복구"하는 현재 안전망을 반드시 유지.
- Redis를 신호 채널로 쓰면 **Redis 내구성(AOF/replica)** 설정이 중요. 지금 Redis는 진행률 캐시·rate limit 용도라 내구성 요구가 낮았음.
- 이 문서의 backend 코드 변경은 **이 저장소를 Java 17로 빌드/테스트할 수 있는 환경**에서 검증해야 합니다(`./gradlew test`). 설계 단계인 지금은 코드 미변경.

## 7. 다음 액션 (승인 필요)

코드 재검토(2.1) 결과 **1a(백오프)는 철회**했고, 남은 후보는 **1b(DLQ 격리 + 관리자 재처리)** 뿐입니다. 다만 1b도 다음 이유로 **가치가 제한적**입니다: 실패한 job은 이미 `FAILED` 상태와 `failReason`으로 보이고, 재시도 한도(`ANALYSIS_RETRY_MAX_COUNT`)가 무한 재시도를 막으며, 관리자 대시보드에서 실패 job을 조회할 수 있습니다. DLQ가 더해주는 것은 "재시도를 소진한 job을 별도 상태로 격리해 한눈에 보고 일괄 재처리"하는 운영 편의 정도입니다.

**권장: 지금은 L5 관련 코드 변경을 하지 않습니다.** 현재 큐 구조는 목표(수평 확장·복구·백프레셔)를 이미 충족하고, 남은 갭(DLQ)은 운영 편의성 수준이라 다른 우선순위 대비 실익이 낮습니다. 5장의 브로커 트리거가 관측되거나, "실패 시 자동 재시도"·"DLQ 운영 편의"가 실제 요구로 올라올 때 이 문서를 근거로 착수하면 됩니다.

> 참고: 이 결론은 backend Java 변경을 이 저장소의 Java 17 환경에서 검증할 수 없는 현재 세션 제약과도 부합합니다. L5 코드는 검증 가능한 환경에서, 명확한 트리거가 생겼을 때 진행하는 것이 안전합니다.
